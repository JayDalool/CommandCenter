## The rule

The CTO keeps the server's disk healthy by tier. Who must say yes depends on what the item is. When an item fits two
tiers, the stricter tier wins.

| Tier | Who says yes | What |
|---|---|---|
| Tier 1 | nobody, the CTO cleans it | Docker build cache; dangling and unused re-pullable images; stopped containers finished over 7 days ago with no mount, compose label or database image; logs over 30 days in the four tool log folders (`~/.npm/_logs`, `~/.vscode-server/data/logs`, `~/.copilot/logs`, `~/.cache/claude-cli-nodejs/*/mcp-logs-*`); leftover worktrees of closed tickets |
| Tier 2 | the project's lead | Anything inside a project's folder, old task data, rollback or preview images a project might return to |
| Tier 3 | Jay | Docker volumes, databases, backups, GauzeMate (client project), live production apps, unknown local images |
| MFE backups | Jay, last resort | Kept for 6 months. Removed only when older than 6 months, absolutely needed, and Jay said yes first. Never part of an automatic run |

After each cleanup the CTO posts in #cto what was removed and how much space was freed, from live disk readings.

## The guard

The CTO's own settings deny the commands that destroy data (`docker volume`, `docker system prune`,
`docker image prune -a`, forced or volume removes, `docker compose down -v`, `rm -rf`, writes under
`/srv/server/backups`). The reviewed template is `scripts/cto/settings.json`. It goes in the CTO-only start folder
`/home/jay/cto`, not `~/.claude/settings.json`, which every agent loads. Jay installs it
([runbook](../runbooks/cto-deny-rules.md)).

These rules are a guard, not a hard stop: prefix matches can be bypassed with `sh -c`, `xargs` or a script, and the CTO
is in the docker group. Jay's drill is the proof that Claude applies them.
