## Policy text

1. Adding a repository starts a formal onboarding workflow. The project enters `mode = "onboarding"`, a sixth mode
   beside Restricted, Controlled Production, Autonomous Product, Experimental Autonomy and Paused.
2. In onboarding, CommandCenter may observe, inspect, sandbox-test, analyze and propose. It holds no credential that
   crosses an authority boundary: no merge, production, database, secret-store, DNS, deploy or payment credential is
   issued. The missing credential is the control.
3. Discovery never runs the project's code with its normal environment or secrets. Builds and tests run in a sandbox
   with no secrets, registry-only network and a throwaway database.
4. CommandCenter builds a Project Fingerprint. Each fact carries an evidence state from D-031, never an AI
   confidence number. Only a deterministic check or Jay can mark a fact verified.
5. A First Project Audit produces a draft Operating Profile as a pull request to `policy/projects/<key>.toml`, which
   is D-007 protected. Until Jay chooses, the file says `mode = "onboarding"` and the proposal sits in a table the
   engine ignores.
6. Proposal pull requests follow D-025: draft only, after a clean deterministic push-safety check, at most 5 open per
   project, and only on Jay's own repositories (clause 16). CI configuration is never pushed or opened as a pull
   request during onboarding without Jay's approval.
7. Graduation needs evidence for the mode being recommended, never time alone. It ends with a Project Admission
   Review. Jay's choice is a hash-bound approval of that review and profile diff, void if either changes.
8. After graduation, drift may tighten a project automatically (D-026), and only Jay loosens it. An aged fact is
   re-checked, never punished by itself (D-031). Re-check intervals start from the configurable defaults in Annex C,
   and a dangerous action always runs its point-of-use check, even when the stored fact is not stale.
9. Existing projects get a baseline audit with graded evidence import and keep their current permissions, except
   that D-026 tightening still applies. Order: CommandCenter, GYST, SamVision, MyFamilyExpenses; GauzeMate only when
   resumed. CommandCenter's admission adds a Codex second opinion, and Jay reviews every finding on a D-007 path.
10. An agent onboards the same way. Creating one writes an identity record with an immutable ID and a versioned
    configuration. It issues no credential and starts nothing. An agent becomes active only through Jay's separate
    activation with Developer Unlock. Its effective permission is its grant, intersected with the project profile,
    the worker's capability and the task mode, and the Broker computes it.
11. No agent may create, register, approve, activate, re-permission or promote itself, another agent or a project.
    No agent may approve its own activation or widen any permission.
12. Under D-032, Slack is at first a notification, approval-request and secure-link surface; CommandCenter stays
    the approval authority. A request goes through a private CommandCenter Slack integration to a private approval
    or alert destination, or a direct message, and shows the risk tier, the agent ID, the project, a concise request
    and an opaque link back to CommandCenter. The link is never an approval credential. Standard and High-risk
    approvals happen inside authenticated CommandCenter; High-risk ones also need Developer Unlock and the existing
    stronger confirmation rules. High-risk permissions, repository access, policy changes and production
    capabilities are never approved by a Slack action alone. Direct Low-risk buttons inside Slack are a later
    capability that needs its own approval and is not enabled. The local ccd API is never exposed publicly for this.
13. Under D-033, onboarding work is billable work inside agent, project and company budgets. A budget hold stops new
    billable work in its own scope only. It never changes a project's mode or authority, and never blocks safety
    monitoring, rollback or recovery.
14. **Engineering hierarchy.** Each project has one Project Lead, who answers to Jay and may supervise specialization
    leads (Frontend, Backend, Security, QA, DevOps and others); they coordinate the agents that report to them. At
    most three levels, with no cycles. Leads delegate work, never authority: an assignment runs with the assignee's
    own permission as the Broker computes it (clause 10), and a lead assigns only inside its own project and
    specialization, and only to agents that report to it. Within the project profile and the project's current
    mode, a Project Lead writes task requirements, acceptance criteria and implementation plans, and splits, orders
    and assigns work, without asking Jay each time. Everything the profile, D-005 or D-007 sends to Jay still goes to
    Jay, including every plan the profile's plan-approval rule names. In onboarding, a lead's routine work is planning
    and proposals only. Agents may propose staffing changes (adding, changing or retiring an agent, with the reason,
    role, reporting line, requested permissions and budget); only Jay decides them (clause 11). The initial Project
    Leads are in Annex C.
15. **Independent review.** A code review counts only when the reviewer had no part in the change: not its
    implementer, a commit author, the plan's author or the lead who assigned the work. The engine picks the reviewer
    from those eligible; the implementer and its lead cannot choose. The review runs in a fresh session from the
    diff, the ticket, the plan and its acceptance criteria, never the implementer's session or notes, and binds to
    the commit it read; a new commit needs a new review. The implementer may answer a finding but cannot close it;
    the reviewer or Jay closes it. High-risk changes and D-007 paths also get a reviewer on a different model family.
    This adds to the reviews the project profile requires and replaces none of them. Until Phase 2 actor tokens can
    prove a reviewer's identity, the engine records independence in shadow.
16. **Repository authority.** During onboarding, CommandCenter may perform only the repository operations in Annex A;
    everything else is refused, and it holds no credential for it. Every push also needs a fresh repository-identity
    check (D-031). A repository whose CI runs on our self-hosted runners always asks Jay before any push. Employer
    and client repositories keep their stricter rules: laptop-only, directed working style, and no push, pull
    request, comment or CI change by CommandCenter during onboarding (D-002, D-022, D-025, D-029). A repository's
    class (Jay's own, employer or client) is set when it is added; an unknown class is treated as client.
17. **Incomplete budget data.** Missing data never makes spend look smaller. Usage with no known price counts at the
    most expensive listed price; usage tied to no project counts toward the company budget; when the meter has no
    fresh reading, spend is Unknown and a scope at or above 80% of its limit starts no new billable work. Each such
    gap raises a data alert. Running work may pass a hard limit only to reach a checkpoint, by at most 5% of the
    limit per scope and period, and expensive steps reserve their estimated cost before they start (Annex B). Beyond
    that, nothing continues past a hard limit without Jay's override or a new limit, and a lead's go-ahead never
    raises or lifts a limit. Safety work is never held, but its spend still counts. Alerts go out at 50%
    (information), 80% (warning) and 95% (urgent) of a limit, and 100% is the hard hold. No permanent dollar limits
    are set yet: the evaluator runs in shadow or soft-warning mode first, and limits are proposed from measured
    usage (Annex B5).
18. **Activation.** Making D-024 final switches nothing on. When Jay turns on shadow mode, the onboarding engine path,
    the reviewer-independence check and the budget evaluator record what they would allow, refuse or hold, and
    enforce nothing. Each enforcement switch (the engine's onboarding mode, Broker credential withholding, agent
    activation and grants, budget holds, approvals inside Slack) is turned on only by Jay's separate, explicit
    approval, and none is requested before all of these hold: Phase 2 actor-token enforcement; a shadow-mode
    validation; the D-030 verification of the laptop runner's privileges and isolation, with recorded evidence that
    personal CI cannot read employer code, credentials or production backups (D-045); and the private authenticated
    approval path (D-006). These are preconditions, never triggers.

**Scope:** global; every new project and agent, and every existing project as a baseline audit.
**Type:** hard boundary (authority actions and repository operations outside Annex A; no agent self-service;
reviewer independence), approval (graduation, agent registration and activation, grants, budget overrides and
limits, each enforcement switch), autonomous (observe, inspect, sandbox, audit, safe draft pull requests, pausing,
a Project Lead's planning and assignment within the profile).

## Annex A · Repository operations during onboarding (clause 16)

| Operation | Jay's own repositories | Employer and client repositories |
|---|---|---|
| Read and clone | Allowed, with a read-only token | On the laptop only (D-002); a server clone needs Jay |
| Edit, commit and branch locally | Allowed (D-025) | On the laptop, in directed style: Jay dictates the work (D-022) |
| Push a branch | Only its own proposal branches (prefix `cc/onboarding/`), through the Broker, after a clean push-safety check and a fresh repository-identity check; never a force push | Never during onboarding; patches stay local and are shown to Jay |
| Open a pull request | Draft only, from a proposal branch, at most 5 open per project; never marked ready, no reviewers requested, no auto-merge | Never during onboarding |
| Comment | Only on its own draft pull requests | Never |
| CI configuration (`.github/workflows/**` and equivalents) | Never pushed or opened as a pull request without Jay's approval, High tier, for each change | Never; their runners are observe-only (D-029) |
| Start or re-run CI | Never by itself; reading results is allowed | Never |
| Merge, rebase a shared branch, delete others' branches, rewrite history | Never: no credential | Never |
| Tags, releases, packages | Never | Never |
| Settings, branch protection, webhooks, deploy keys, secrets, environments, collaborators | Never: no admin credential | Never |
| Create, fork, rename, archive or delete a repository | Never | Never |

The push-safety check (D-025) must prove a push will not deploy code, run privileged CI, expose production secrets,
call production webhooks, change production infrastructure or data, send external communication, create meaningful
cost, or reach another project. True or unknown on any line: stop and ask Jay. For employer and client
repositories, Slack requests carry identifiers and the risk summary only, never code or file contents, and an
agent's session on one is never reused in another project. Jay himself may still push to any repository; these rows
limit CommandCenter.

## Annex B · Budgets when data is incomplete, the overrun, and expensive steps (clause 17)

Approved starting defaults (Jay, 2026-10-24T06:51Z). They are configurable per scope later and are tuned with
real usage evidence; none is a fixed constant.

**B1. Missing data never lowers spend.** Status: built in the shadow report (`server/ccd/budgets.py`, merged in
#65, flag off).

| Gap | What CommandCenter does |
|---|---|
| A reply with no known price (Codex, a new model) | Counts at the most expensive listed price of each kind, today $10 input and $50 output per million tokens; any budget may also set a token limit. Data alert `unpriced-usage`. |
| Price list older than 90 days | Data alert `price-list-old`; the listed prices stay in use until updated. |
| Usage tied to no project | Counts toward the company budget. Data alert `unattributed-usage` above 10% of the month's spend, and `unbudgeted-usage` when no company budget is set to count it. |
| Usage not yet tied to an agent | Agent lines count what work steps report. Until Phase 2 ties sessions to registered agents, project and company limits are the ones that hold, and they count everything measured. |
| No successful meter reading for 15 minutes (or none since start) | Spend is Unknown: the line's state is `unknown`, and a scope at or above 80% of its limit would hold new billable work (`holdReason: stale-meter`). Data alert `meter-stale`. Safety work is unaffected. |

**B2. The 5% overrun.** Room for steps already running at a hard limit to reach a safe checkpoint, and nothing
more:

- It covers only steps that were running when the hold began; no new work starts on it.
- It is per scope and per period and does not stack: an agent's overrun also counts toward its project and the
  company, and the tightest cap wins.
- At the limit plus 5%, running billable steps in that scope stop at the next tool-call boundary and checkpoint
  (D-027). A deploy, migration, rollback or push already under way follows its existing atomic-operation safety
  rules and may finish past it.
- It is measured on the meter's estimate, which lags and uses list prices, so the bill can differ.
- On a small limit it is small ($1 on a $20 daily agent limit), which one large step could pass; B3 prevents that.

**B3. Expensive running steps** (approved; not built):

1. Reserve before starting: each billable step carries an estimate from its model, token ceiling and expected
   turns, and starts only if spend, running reservations and its estimate fit every budget around it.
2. A cap per step: 25% of the agent's daily budget or $10, whichever is lower. A billable step that reaches it
   checkpoints rather than continuing blindly, and asks its lead before it continues; beyond that it comes to Jay.
3. Large steps: an estimated cost above $10 needs the Project Lead's approval, above $25 Jay's. A go-ahead never
   raises or lifts a limit.
4. Burn-rate breaker: when a scope spends more than 25% of its daily allocation within one hour, it starts no new
   billable steps, running work continues only to a checkpoint, Jay gets an alert, and the cause is investigated as
   possible runaway behaviour.
5. Runaway detection: a step that repeats the same failing action, or makes no progress for 10 turns, checkpoints
   and stops.
6. Checkpoints at least every 15 minutes in long steps. A critical operation declares its expected cost and starts
   only when that much room is left, so it never needs to be cut off.

**B4. Alerts** (approved): 50% of a limit is informational, 80% a warning, 95% urgent, and 100% the hard hold. Each
is sent once per period, plus a warning when the run rate would reach the limit before the period ends.
Configurable per scope later.

**B5. Budget amounts.** No permanent dollar budgets are set yet. The budget evaluator runs in shadow or soft-warning
mode first and gathers real usage. Once enough representative usage exists, CommandCenter proposes agent daily and
monthly limits, project limits and a company limit, each with its evidence, for Jay to decide.

## Annex C · Starting defaults: fact re-verification and Project Leads

Approved by Jay on 2026-10-24T06:51Z as starting defaults, configurable in policy, not universal constants.

**C1. Fact re-verification** (D-031, which records the same defaults). Each fact class has its own interval instead of one universal 30-day rule.

| Fact | Re-verify |
|---|---|
| Architecture and framework | About every 90 days, or sooner when a code change invalidates it |
| Hosting, DNS and deployment configuration | About every 30 days |
| Backup success and state | Every backup cycle |
| Restore capability | A periodic restore drill, as the project's policy sets |
| Worker online state | Live, with a short TTL |
| Worker identity and capability | Freshly, before privileged execution |
| Repository identity | Freshly, before a push or merge |
| Production deploy target | Freshly, before a deploy |
| Production database target | Freshly, before a migration |

Other fact classes keep D-031's proposed defaults until set. A dangerous action always performs its point-of-use
verification, even when the stored fact is not technically stale.

**C2. Initial Project Leads** (also recorded in the operating rules as D-046).

| Project | Project Lead |
|---|---|
| CommandCenter | Claude Project Lead |
| GYST | Claude Project Lead |
| SamVision | Claude Project Lead |
| MyFamilyExpenses | Claude Project Lead |
| GauzeMate | None while the project is paused |

"Claude Project Lead" is a stable agent role and persona, not one exact model version. The backing model may change
while the agent's identity and work history stay intact. Each project's assignment and history stay separate, even
where the same lead persona serves several projects. Dedicated leads may be onboarded later, through clause 10.
